# NDL — Noematica Design Language

> 色彩、字體、Spacing、Elevation、動畫、元件狀態、Asset 規範、命名規範。這份文件不需要知道 Noematica 的資料模型（Entity/Atom/Observation 是什麼）也能讀懂——它定義的是「這個視覺系統本身長什麼樣子」，不是「知識概念怎麼被畫出來」（那是 NUG 的範圍，見 `NUG.md`）。

> 圖片/素材的詳細技術規格（尺寸、格式、切片座標、命名）在 `NAL.md`，這份文件只講原則。

---

## 0. 這份文件從哪裡來

不是憑空設計的規範。每一條規則背後都對應一個實際踩過的坑或做過的決定，引用了現有程式碼裡的真實數值（`hud.css`、`theme.json`、`hud-panels.js`），不是抽象範本。文件裡標記「⚠️ 教訓」的段落，都是這個系統實際發生過的錯誤，記錄下來是為了不要再犯第二次。

**跟 NUG 的邊界**：這份文件只回答「顏色/字體/間距的值是什麼、規則是什麼」，不回答「哪個知識概念該用哪個顏色」——後者一律去查 `NUG.md`，這裡不重複。

## 1. 核心原則：元件自治（Component Autonomy）

> ⚠️ **教訓**：第一版做面板美術皮膚時，把整張參考稿（含標題列、分類頁籤、道具格、底部按鈕列全部畫在同一張圖裡）當成一整塊 `border-image` 貼上容器，結果版面計算全部打架、東西擠成一團、按鈕點擊失效。根本原因：**用一張排版死的靜態稿去對齊一個由 flex/grid 動態排版的活介面**，只要真實資料筆數、視窗尺寸跟稿子預設的不一樣，兩邊就會打架。

**規則**：每一個 UI 區塊管自己的一塊獨立方框，自己決定要用什麼背景（純色／漸層／貼圖），彼此之間**不互相依賴絕對座標**。**美術要遷就框架，不是框架遷就美術**。細節技術規則見 §7 跟 `NAL.md`。

## 2. 色彩系統

### 2.1 三層色彩哲學

| 層級 | 定義 | 換主題時 |
|---|---|---|
| **Tier 1：美觀色（Aesthetic）** | 純粹視覺偏好，不帶意義 | 跟著換 |
| **Tier 2：識別色（Identity）** | 特定功能/模組的招牌色，用來讓使用者快速辨認「這是哪一個」 | 不換 |
| **Tier 3：語意色（Semantic）** | 帶有意義的顏色（例如「這是正向的」「這是危險的」），使用者已經對它形成直覺 | 不換 |

判斷準則：換主題時這個顏色變了，使用者會不會誤讀資訊？會的話歸 Tier 2 或 Tier 3，不會的話歸 Tier 1。

**Tier 2 和 Tier 3 的差別**：Tier 2 回答「這是哪一個」（辨識/導航），Tier 3 回答「這是好是壞/強是弱」（狀態判讀）。同一個顏色理論上不該同時身兼兩職——如果一個模組的識別色剛好跟某個語意色重複，純屬巧合，不代表這個模組「等於」那個語意。

### 2.2 Tier 1：美觀色 Token（跟主題走）

來源：`application/frontend/hud.css` 的 `:root`，執行期由 `applyTheme()` 用 inline style 覆蓋，值來自 `theme.json`。

| Token | 預設值 | 用途 |
|---|---|---|
| `--accent` | `#E8C873` | 主強調色 |
| `--accent2` | `#F5A623` | 次強調色 |
| `--text` | `#f0ead8` | 主要文字 |
| `--muted` | `rgba(255,255,255,0.35)` | 次要/停用文字 |
| `--border` | `rgba(232,200,115,0.22)` | 一般邊框 |
| `--border2` | `rgba(232,200,115,0.60)` | 強調邊框 |
| `--panel-bg` | `rgba(8,14,28,0.97)` | 面板底色 |
| `--key-bg` | `rgba(0,0,0,0.48)` | 熱鍵圓鈕底色 |
| `--quest-bg` | `rgba(0,0,0,0.58)` | 任務欄底色 |
| `--overlay-color` | `rgba(0,0,0,0.82)` | 全螢幕遮罩 |
| `--bg-blur` | `4px` | 背景模糊強度 |
| `--hp-l` / `--hp-r` | `#4CAF50` / `#8BC34A` | 漸層色對（目前用在 HP 條，語意上屬於 Tier 1，因為它只是「一組好看的綠色漸層」，不代表特定狀態判讀） |
| `--key-size` | `46px` | 熱鍵圓鈕尺寸 |

新增主題只要填 `theme.json` 的 `colors`/`assets`/`layout` 三個區塊（完整 schema 見 `NAL.md` §3），不用改 CSS。

### 2.3 Tier 2：識別色（固定）

| 識別對象 | 顏色 | Hex |
|---|---|---|
| 功能 1 | 金（同 `--accent`，刻意呼應主色，代表預設/首要功能） | `#E8C873` |
| 功能 2 | 天藍 | `#4fc3f7` |
| 功能 3 | 粉紅 | `#f472b6` |
| 功能 4 | 橘 | `#F5A623` |
| 功能 5 | 紫 | `#A97FE8` |
| 功能 6 | 青綠 | `#4ECDC4` |
| 功能 7 | 淺紫（跟功能 5 的紫刻意區隔一階，不要再往這個色相加第三個） | `#a78bfa` |
| 系統動作（非功能，例如關閉/設定） | 中性灰藍 | `#94a3b8` |

這張表只列「有幾種識別色、彼此如何區隔」——**哪個顏色對應系統裡的哪個具體功能，是產品層的資訊，不影響這份文件要講的規則**，故意不寫死功能名稱，避免這份文件因為功能改名/重排就要跟著改。

### 2.4 Tier 3：語意色（固定）

| 語意 | 顏色 | Hex |
|---|---|---|
| 正向／完成／強 | 綠 | `#4ade80` |
| 警示／中等 | 琥珀 | `#fbbf24` |
| 進行中（例外色，不用琥珀） | 紫 | `#A97FE8` |
| 弱／資訊性 | 藍 | `#60a5fa` |
| 中性／略過 | 灰 | `#94a3b8` |
| 負向／失敗／危險 | 紅 | `#f87171` |

**規則**：任何新的三態或四態狀態指示，一律沿用這六個色碼，不重新調色。「進行中」固定用紫色（跟琥珀色的「警示」區分開——進行中不是警示，是中性的過程狀態）。

## 3. 字體

| 角色 | 字體 | 用途 |
|---|---|---|
| UI／資料／程式碼 | `JetBrains Mono` | 所有介面文字、數值、輸入框、按鈕標籤——等寬字體，數字對齊 |
| 標題／裝飾性文字 | `Noto Serif SC` | 大標題、強調性文字——襯線字體，不進入內文 |

### 3.1 字級 Scale

現況是每個元件各自手調（9px～16px 散值），目標收斂成：

| Token | 大小 | 用途 |
|---|---|---|
| `--fs-xs` | `9px` | 極小標籤（按鈕內縮小文字、角標） |
| `--fs-sm` | `11px` | 次要文字、表單標籤 |
| `--fs-base` | `13px` | 內文預設 |
| `--fs-lg` | `16px` | 小標題 |
| `--fs-xl` | `20px` | 主標題 |

現有元件尚未全面遷移到這組 token，新元件一律直接用這組，不再手調 px。

## 4. Spacing

現況是散值（`padding`/`gap` 常見值：4/5/6/7/8/10/12/14/20px，沒有統一格線）。目標收斂成 4px 基準格線：

| Token | 大小 |
|---|---|
| `--sp-1` | `4px` |
| `--sp-2` | `8px` |
| `--sp-3` | `12px` |
| `--sp-4` | `16px` |
| `--sp-6` | `24px` |
| `--sp-8` | `32px` |
| `--sp-12` | `48px` |

**規則**：新元件的 `padding`/`gap`/`margin` 一律從這組 token 選，不新增中間值（例如不要 `10px`，往上取 `--sp-3`(12px) 或往下取 `--sp-2`(8px)，寧可視覺上略有落差也要維持格線一致性）。既有元件不強制遷移，但修改既有元件時順手對齊。

## 5. Elevation（層級）

現況 z-index 實際用到 `0,1,2,4,5,6,10,11,30,40`，沒有正式分層規則。收斂成：

| 層 | z-index 範圍 | 用途 |
|---|---|---|
| `--z-base` | `0–9` | 一般面板內容（面板本體、side bar、grid） |
| `--z-overlay` | `10–19` | 面板內的懸浮熱區（例如蓋在美術邊框上的按鈕熱區） |
| `--z-modal` | `20–29` | Modal 本體／backdrop |
| `--z-toast` | `30–39` | Toast／短暫通知 |
| `--z-top` | `40–49` | 設定面板等最高優先層 |

陰影（目前只在 Modal 開啟時用，`box-shadow: 0 24px 70px rgba(0,0,0,0.55)` 這類大範圍柔和陰影）：層級越高，陰影越大越柔——不使用生硬的小陰影（跟整體「柔和/手繪」美術調性不合）。

## 6. 動畫

| Token | 時長 | 用途 |
|---|---|---|
| `--motion-fast` | `120ms` | hover 狀態變化 |
| `--motion-base` | `160ms` | 一般過場（toast、面板展開） |
| `--motion-slow` | `200ms` | modal 開關、大範圍位移 |

**規則**：

- 只對 `transform`/`opacity` 做動畫，避免 layout thrashing。
- 尊重 `prefers-reduced-motion`（現況未處理，待補）。
- 不做「為了熱鬧而動」的動畫，克制優先於花俏。

## 7. 元件狀態

任何互動元件（按鈕、卡片、頁籤）都應該定義以下狀態，不是每個都要有視覺差異，但都要「想過」：

| 狀態 | 視覺規則 |
|---|---|
| Normal | 基準樣式 |
| Hover | 邊框色或背景輕微變化（用 `--motion-fast`），不改變尺寸避免 layout shift |
| Active/Selected | 語意色或識別色標示（依情境判斷用哪一層，見 §2.1），通常搭配較高對比 |
| Focus（鍵盤導覽） | **現況缺失**，待補——目標是清楚可見的 outline，不能只靠 hover 樣式頂替（滑鼠跟鍵盤是兩種輸入模式） |
| Disabled | 降低透明度（建議 40~50%）+ `pointer-events: none`，不用單獨的灰階配色系統 |
| Empty（容器類元件沒有內容時） | 見 §7.1 |

### 7.1 空狀態規則

格狀容器（例如收藏列表、清單類元件）資料筆數不足以填滿視覺區域時，用**空元素填充**維持容器的視覺完整性，不要讓容器縮成剛好資料筆數的大小。空元素：

- 使用跟實體元素相同的背景/框線樣式
- 不可互動（`pointer-events: none`）
- 視覺上可以降低透明度或飽和度區分「有內容」跟「空的」，但不要用完全不同的樣式（不然看起來像壞掉）

## 8. Asset 規範（原則）

完整技術規格（尺寸、格式、切片座標、命名、交付檢查表）見 `NAL.md`。這裡只列這份文件層級該知道的原則：

1. 一張素材只服務一個 CSS 盒子（§1 元件自治的直接推論）。
2. 沒有對應功能的裝飾元素，不做假熱區——沒有功能就讓它是背景的一部分，不能點，不要做點了沒反應的假按鈕。
3. 素材缺失時的降級行為屬於 Asset 規範的一部分：一律降級到「還能用的樣子」（例如退回內建圖示），不能整個壞掉或空白。

## 9. 命名規範

### 9.1 CSS Custom Property（Design Token）

`--kebab-case`，語意優先於數值（例如 `--accent` 不是 `--gold-e8c873`）。跟主題相關的 token 直接對應 `theme.json` 的 `colors`/`layout` 欄位名稱（駝峰轉 kebab，例如 `keyBtnSize` → 概念上對應 `--key-size`）。

### 9.2 CSS Class

現況慣例（延續既有程式碼，不重新發明）：

- 功能模組前綴 + 語意後綴，例如 `m-item`、`m-sidebar`、`m-detail`（`m-` = modal content 底下的共用元件）、`hk-ico`、`hk-lbl`（`hk-` = 熱鍵相關）。
- 每個功能面板的美術皮膚統一命名 `modal-skin-<面板id>`（例如 `modal-skin-b`），面板 id 直接對應功能鍵位小寫（`f1`/`f2`/.../`b`/`h`/`m`），不額外發明別名。
- 狀態用單純的形容詞 class 疊加，不用 BEM 的 `--modifier` 語法（例如 `.m-cat.active`，不是 `.m-cat--active`）——延續現有程式碼慣例。
