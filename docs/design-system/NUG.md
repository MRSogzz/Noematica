# NUG — Noematica UI Grammar

> 只描述 Entity、Atom、Observation、Activation、Confidence 這五個知識概念如何映射到視覺語言（用什麼顏色語意、什麼視覺強弱），不談 CSS、不談 Figma、不談元件怎麼實作。讀這份文件不需要懂前端技術，只需要懂 Noematica 的知識模型是什麼。

> 顏色/字體/間距的實際數值定義在 `NDL.md`，這份文件只說「哪個概念對應 NDL 的哪一層語言」，不重複列出色票。實作層的元件規格（props、CSS class、閾值判斷邏輯寫在哪個檔案）屬於 Frontend Component Library 的範圍，不在這份文件裡。

---

## 0. 為什麼需要這份文件

系統裡有五個核心知識概念：**Entity**（實體）、**Atom**（實體之間的關係）、**Observation**（支持或反對一個 Atom 的觀測證據）、**Confidence**（一筆推論有多可信）、**Activation**（查詢時被「喚醒」、判定為相關的知識）。

這五個概念目前有些已經有視覺呈現、有些完全沒有、有些呈現方式只存在於單一畫面、沒有被記錄成規則。這份文件把「這個知識概念該讓人感覺到什麼」統一講清楚，讓不同的畫面、不同的人做出來的東西，讀者感覺是一致的。

**跟 NDL 的邊界**：這份文件只講「Entity 的類型該傳達出什麼視覺強弱／哪一種語意」，不講「那個顏色的十六進位色碼是多少」——色碼查 `NDL.md`。

---

## 1. Entity（實體）

Entity 代表知識網路裡的一個節點——一個概念、一個指標、一個技術、一個組織。Entity 有一個「類型」屬性，決定它在視覺上該傳達什麼樣的形象：

| Entity 類型 | 該傳達的視覺形象 |
|---|---|
| 概念（抽象想法） | 抽象、想法感——例如燈泡/星芒這類「靈感」意象 |
| 指標（可量化的數值） | 數據感——例如圖表/趨勢線意象 |
| 問題（待解決的陳述） | 警覺但不是危險——不用語意色的紅，用一個中性的「待處理」符號 |
| 流程（一連串步驟） | 動態、順序感——例如箭頭/齒輪意象 |
| 技術（具體方法） | 工具感——扳手/零件意象 |
| 組織（公司等） | 結構感——建築/機構意象 |
| 總經變數 | 政策/總體感——與「指標」相近但更強調外部性 |
| 未分類 | 一律要有預設形象，不可留空 |

**規則**：Entity 的類型只決定「用什麼形象」，不直接決定顏色——類型之間不用顏色互相區分（因為一個 Entity 可能同時屬於多個知識領域標籤，用單一顏色編碼類型，會在「領域標籤」也想用顏色表達時互相衝突）。類型用「形象/符號」區分，領域用文字標籤區分，兩者不共用同一個視覺維度。

---

## 2. Atom（關係）

Atom 代表兩個 Entity 之間的一段推論關係（例如「A 導致 B」「A 與 B 相關」「A 是 B 的定義」）。Atom 有一個「類型」，這個類型隱含一個**推論可靠度**的高低（由系統的信心計算引擎決定，數值上定義成立、限制類的關係本質上比類比、經驗法則類的關係更可靠）：

| 可靠度層級 | 包含的關係類型 | 該傳達的視覺強弱 |
|---|---|---|
| 最高 | 定義、限制 | 最確定、最肯定的視覺呈現方式 |
| 中等 | 因果 | 一般肯定 |
| 中低 | 相關 | 明確標示「這只是相關，不是因果」的視覺區隔——不能讓人誤以為跟因果一樣肯定 |
| 較低 | 經驗法則 | 帶有「這是經驗談，不是嚴謹推導」的暫定感 |
| 最低 | 類比 | 最不確定、最暫定的視覺呈現方式，讓人一看就知道這是類比推論，不是結論 |

**規則**：可靠度層級決定的是「這段關係的視覺確定感（例如線條的實/虛、粗/細、濃/淡）」，**不是顏色**。顏色維度保留給 §4 的信心分級（Confidence）——「這是什麼類型的關係」跟「這個關係現在算出來有多可信」是兩件不同的事：同一個類型的關係，可能因為證據多寡而算出不同的信心值；反過來，即使是類比這種先天不確定的類型，只要有大量獨立證據佐證，信心值也可能不低。兩個視覺維度疊加起來，才是一段關係的完整呈現，不能只看其中一個。

---

## 3. Observation（觀測／證據）

Observation 是支持或反對一個 Atom 的一筆具體證據，有一個「立場」屬性：支持、反對、或中立（沒有明確倒向哪一邊）。

| 立場 | 該傳達的視覺語意 |
|---|---|
| 支持 | 使用 NDL 「正向」語意色的語言 |
| 反對 | 使用 NDL 「負向」語意色的語言 |
| 中立 | 使用 NDL 「中性」語意色的語言，**不是**「弱」語意色——立場中立跟信心偏弱是兩件不同的事，不可混用同一種視覺語言 |

**規則**：立場的視覺語言只用在單筆 Observation 這個層級，**不要**跟 Atom 整體的信心視覺語言（§4）用同一個視覺元素表達。一個是「這一筆證據支持還是反對」，一個是「把所有證據綜合起來，整體推論有多可信」——把兩個不同層級的判斷疊在同一個顏色上，會讓人分不清這個顏色到底在講哪一件事。

---

## 4. Confidence／Activation（信心與喚醒）

當使用者查詢知識時，系統會沿著 Entity/Atom 構成的網路，把跟查詢相關的知識「喚醒」（Activation），並依照信心高低分成四個等級：

| 等級 | 該傳達的視覺語意 | 何時成立 |
|---|---|---|
| 強 | NDL「正向」語意色的語言 | 信心分數達到系統定義的高信心門檻 |
| 中 | NDL「警示」語意色的語言 | 信心分數落在中間區間 |
| 弱 | NDL「弱／資訊性」語意色的語言 | 信心分數落在偏低區間，但還不到棄權的地步 |
| 隱藏 | 不呈現——低於雜訊門檻的東西，不該出現在使用者眼前跟強/中/弱的東西並列，那只會製造雜訊，不是資訊 | 信心分數低於系統定義的棄權門檻 |

**規則**：信心分級是一個**離散的分類判斷**，不是連續的漸層量——系統在門檻上有明確的行為分界（例如低於某個門檻會直接判定「證據不足、拒絕回答」），視覺呈現也該反映這個「有明確分界」的事實，不要用連續漸層的顏色去暗示信心是一個平滑變化的量，那會誤導使用者以為「差一點點」的信心值視覺上也該差一點點，但系統的實際行為（例如是否棄權）在某些門檻上是非黑即白的。

**棄權**：當證據不足、系統判定無法給出可信回答時，這個狀態該傳達的視覺語意跟「中」等信心相同（都是「不確定、需要謹慎看待」），但要搭配明確的文字說明「證據不足」，不能只靠顏色讓使用者自己猜為什麼看不到答案。

---

## 5. 五個概念如何一起呈現

以「使用者展開一段知識關聯」為例，一次完整的呈現同時牽涉到上面四節講的視覺語言，缺一不可：

1. 兩端的 Entity → 各自的類型形象（§1）
2. 連接它們的 Atom → 類型決定的確定感強弱（§2）
3. 底下支持這段關係的 Observation → 各自的立場語意色（§3，通常只在使用者要求「看細節」時才展開，不是預設就全部攤開）
4. 整段推論的信心 → 分級語意色（§4）

這四層彼此獨立、可以同時存在但互不覆蓋——這是這份文件最重要的原則：**每一層知識概念都有自己專屬的視覺維度**（形象／確定感的實虛粗細／立場色／信心分級色），不要為了畫面簡潔把兩層概念硬塞進同一個視覺元素，那樣使用者會失去分辨「這個顏色到底在講哪一層」的能力。

## 6. 待確認事項

- Observation 的「中立」立場，目前實際資料裡還沒有出現過真實案例（系統邏輯上有處理這個狀況，但還沒有真實資料驗證過對應的視覺呈現看起來如何），建議之後有真實中立案例時重新檢視一次。
- Entity 類型清單目前資料裡存在同一類型大小寫不一致的情況（例如同一個類型有時大寫開頭有時全小寫），這是資料品質問題，不影響這份文件定義的視覺規則，但建議在資料源頭一併整理。
