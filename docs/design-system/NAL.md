# NAL — Noematica Asset Language

> 圖片/美術素材的技術規範：格式、尺寸、切片方法、命名、交付檢查表。這份文件是給「要產出或處理美術素材」的人看的（不管是人類設計師還是 AI 產圖），目的是讓每一份素材從一開始就照著能被 NDL §1（元件自治原則）正確使用的方式切好，而不是交付一張排版死的整體 mockup 之後才發現前端組不起來。

> 色彩/字體/間距等視覺 token 定義在 `NDL.md`；知識概念該傳達什麼視覺語意在 `NUG.md`；素材切好之後，視窗在螢幕上實際該顯示多大（縮放倍率、安全區、跟 `.modal` 尺寸的對應關係）在 `NWL.md`。這份文件不重複那兩份/那一份的內容，只講「素材檔案本身」的規格——本文件裡的切片 px 數字是「原圖座標」，不是螢幕顯示尺寸，兩者的換算規則見 `NWL.md`。

---

## 0. 這份文件要解決的問題

> ⚠️ **完整案例**：第一輪拿到的參考圖是一張 851×882 的完整背包視窗 mockup——標題列、徽章、8 個分類頁籤、35 個道具格、底部貨幣列、4 顆功能按鈕全部畫在同一張圖裡。直接把它當一整塊 `border-image` 貼上容器，因為圖裡的頁籤數量（8 個）跟系統實際的分類數量（4 個）對不上、圖裡的道具格是固定 35 格但實際模組數量是變動的、關閉鈕的絕對座標换了個瀏覽器尺寸就對不齊——最後版面全部打架，側欄跟格子的點擊事件也被意外蓋住的透明熱區擋住。

**根本原因**：一張完稿 mockup 呈現的是「這個介面在某個特定時刻、某個特定資料量下長什麼樣子」，但真正的介面是動態的——分類數量會變、資料筆數會變、視窗尺寸會變。要讓美術真的能用，必須先把 mockup **拆解成一個一個獨立的元件級素材**，每個素材只負責填滿一個獨立的 CSS 盒子，不假設自己旁邊/上下有什麼東西。

這份文件定義的就是「怎麼拆」跟「拆完之後怎麼命名/怎麼標記給前端用」。

## 1. 核心規則：一張素材、一個盒子

跟 NDL §1 是同一條原則，這裡給出可執行的判斷標準：

**在裁一張素材之前，先問**：這張圖要貼到 CSS 裡的哪一個元素？那個元素的大小是固定的，還是會隨資料/視窗變動？

- 如果那個元素大小固定、內容也固定（例如一顆按鈕的圖示）→ 裁一張剛好包住這個元素內容的獨立小圖，直接當 `background-image`。
- 如果那個元素數量會變動（例如格狀清單裡的一格）→ 裁一張「單位元素」的紋理（例如一個空格子），前端會重複套用在每一個格子上，**不要**交付「N 個格子排在一起」的整塊圖。
- 如果那個元素是「外框」性質（例如視窗邊框）→ 用九宮格切片（見 §4），只切邊框本身的細條，中間鏤空讓真實內容顯示。
- 如果稿子裡有「示範用但沒有對應真實功能」的裝飾元素（例如稿子畫了縮小鈕但系統沒有縮小功能）→ 那個區域要嘛裁進純裝飾的邊框素材（不能點），要嘛乾脆不裁，不要裁成一個看起來能點但沒接功能的獨立素材。

## 2. 命名規範

### 2.1 檔案命名模式

```
<面板id>_<元件>[_<狀態>].png
```

| 欄位 | 說明 | 範例 |
|---|---|---|
| 面板 id | 對應 NDL §9.2 的面板 id（`f1`/`f2`/.../`b`/`h`/`m`） | `b`、`h` |
| 元件 | 這張圖服務的具體元件，用英文描述性名稱 | `frame`（外框九宮格）、`slot`（格子紋理）、`close`（關閉鈕）、`badge`（形象徽章）、`titlebar`（標題列紋理）、`tab`（頁籤） |
| 狀態（選填） | 只有需要獨立美術的狀態才加，能用 CSS 濾鏡做出來的狀態不裁（見 §5） | `active`、`inactive` |

範例（實際案例）：`b_frame.png`、`b_slot.png`、`b_close.png`、`b_badge.png`、`b_titlebar_tile.png`、`b_tab_active.png`、`b_tab_inactive.png`、`b_btn_backpack.png`、`b_btn_trash.png`、`h_frame.png`。

### 2.2 目錄結構

```
application/frontend/assets/
├── themes/<theme-id>/theme.json      — 主題設定檔（見 §3）
│   ├── bg.jpg / minimap.png / avatars/*.png / keys/*.png
└── panel-art/<面板id>_<元件>.png     — 面板專屬素材（不隨主題切換，見 §7 討論）
```

## 3. `theme.json` 完整 Schema

```jsonc
{
  "name": "主題顯示名稱",
  "colors": {
    "accent": "#E8C873", "accent2": "#F5A623",
    "text": "#f0ead8", "muted": "rgba(255,255,255,0.35)",
    "border": "rgba(232,200,115,0.22)", "border2": "rgba(232,200,115,0.60)",
    "panelBg": "rgba(8,14,28,0.97)", "keyBg": "rgba(0,0,0,0.48)",
    "questBg": "rgba(0,0,0,0.58)", "overlayColor": "rgba(0,0,0,0.82)",
    "bgBlur": "4px", "hpColor": "#4CAF50", "hpColor2": "#8BC34A"
  },
  "assets": {
    "bg": "assets/themes/<id>/bg.jpg",
    "minimap": "assets/themes/<id>/minimap.png",
    "keys": { "f1": "...", "f2": "...", "...": "...", "m": "..." },
    "avatars": { "0": "...", "1": "...", "2": "..." }
  },
  "layout": {
    "minimapSize": 130, "keyBtnSize": 44, "charCardWidth": 52
  }
}
```

**規則**：`colors`/`layout` 裡每一個欄位都要填，不接受部分欄位（避免有些主題看起來「一部分換了、一部分沒換」的不一致狀態）。`assets.keys` 不要求全部 8 個鍵位都有圖——沒有圖的鍵位會自動退回內建 SVG 圖示（見 §8 降級規則），但**建議**新主題至少把最常用的幾個鍵位（依產品判斷）補齊，不要交付一個只有顏色、完全沒有任何圖片的「半成品主題」。

## 4. 九宮格外框（Border-Image）規範

### 4.1 什麼時候用九宮格，什麼時候不用

**用**：一個固定的視窗外框（標題列＋左右邊框＋底部邊框），中間內容是動態的。九宮格只切「邊框」的細條，**不對中間內容做 fill**（`border-image-slice` 不加 `fill` 關鍵字）——中間讓真實的 DOM 內容（純色背景＋真實子元件）顯示，不要把 mockup 裡畫的示範內容也一起貼上去。

**不用**：任何裡面有多個獨立可互動元件、且元件數量或位置會變動的區域（例如頁籤列——頁籤數量是資料決定的，不是美術決定的，這種情況每個頁籤各自裁成獨立素材，見 §2.1）。

### 4.2 切片座標怎麼量

**不用眼睛估，用色塊邊界掃描**。方法：

1. 沿著圖片中線（避開角落的徽章/按鈕等裝飾）做垂直掃描，逐像素比對相鄰顏色的差異，找出「標題列結束、內容區開始」「內容區結束、底部列開始」的 y 座標。
2. 同樣方式做水平掃描，找出左右邊框的厚度。
3. 掃描時**要避開裝飾性內容**（例如掃描線剛好經過按鈕上的圖示細節，會產生很多假的邊界訊號）——選一條乾淨、只穿過純色/材質背景的線。
4. 量出來的四個數字（上/右/下/左，單位 px，對應原圖實際解析度）就是 `border-image-slice` 跟 `border-image-width` 的值，兩者用一樣的數字（避免縮放模糊）。

### 4.3 切片範圍的界定原則

九宮格的「上邊」切到哪裡結束，取決於**這個區域是純裝飾還是含有真實互動元件**：

- 只到標題列結束（不含頁籤列）：如果頁籤/分類是真實可互動的 DOM 元件（見 §4.1「不用」的情況）。
- 含整個標題列＋頁籤列：如果那個區域完全是裝飾、沒有任何真實互動元件需要疊上去。

拿不準的時候，切小一點（只保留確定是純裝飾的部分），把有疑慮的區域讓給真實 DOM——切太大、之後發現裡面其實需要真實互動元件，要重新切一次圖；切太小，最多只是裝飾範圍變保守，不會造成功能性問題。

### 4.4 已知案例（供參考）

> ⚠️ **這張表曾經跟前端實作對不上**：下面 851×882／517×404 那兩列是 §0 提到的第一輪失敗 mockup 量出來的數字，後來 `b_frame.png`／`h_frame.png` 都換成重新裁過的素材（見下方「目前有效」表），但這張表沒有跟著更新——如果照舊表的切片數字去對照新素材或去寫 CSS，切片座標會整組是錯的。**現在起，切片數字一律以下方「目前有效」表 + 對應的 `assets/panel-art/<素材>.json`（frame metadata）為準**，這張表也是唯一允許出現在 `panel-skins.css` 裡的數字來源；舊表格只留著當歷史紀錄，不再是可信來源。

**目前有效**（跟 `docs/design-system/manifest.json` 及 `application/frontend/assets/panel-art/*_frame.json` 同步，任何一邊改動都要三邊一起改）：

| `h_frame.png` | 360×377 | 84 / 22 / 23 / 16 | 取代舊版 517×404 那份；沒有頁籤列，上邊含整個標題列＋徽章＋關閉鈕裝飾（**烤入的徽章不可單軸拉伸**，見 NWL.md） |

## 5. 狀態變體：哪些要裁圖，哪些用 CSS 做

不是每個互動狀態都需要獨立美術檔案：

| 狀態 | 需要獨立素材？ | 說明 |
|---|---|---|
| Normal | 是 | 基準美術 |
| Hover | 否，用 CSS `filter: brightness()` 處理 | 除非美術上 hover 要換完全不同的圖案（少見），否則濾鏡就夠 |
| Active/Selected | 視情況 | 如果 active 狀態的視覺差異只是「變亮/加邊框」，用 CSS；如果是完全不同的圖案（例如頁籤選中變成完全不同顏色系的圖案，不是同一張圖調亮），才裁獨立素材（例：`b_tab_active.png` / `b_tab_inactive.png`） |
| Disabled | 否，用 CSS `opacity` + 去飽和濾鏡 | — |
| Empty（占位格） | 否，重複使用 Normal 素材 | 見 NDL §7.1，空格子用跟實體格子一樣的紋理，不裁專門的「空格」圖 |

**判斷原則**：先假設所有狀態都能用 CSS 濾鏡從同一張 Normal 素材做出來；只有濾鏡做不出來的差異（色系整個換掉、圖案本身不同），才要求裁獨立素材。裁越多獨立素材，之後要維護/替換的檔案就越多，非必要不要裁。

## 6. 視窗邊框素材規格（角落圖示 / 邊條）

> 這節是寫給要修改或新增角落圖示、邊條材質的人看的規格。目前的邊框架構（見 `NWL.md`）已經不是「一張 `xxx_frame.png` 切九宮格當 `border-image`」，而是**四個角落跟邊條完全分開**：角落是各自獨立的小張 PNG（固定尺寸、不受響應式縮放影響），邊條直接用 CSS 邊框顏色模擬，不用圖片。這是第三版的架構調整，取代本節先前描述的「`border-image-repeat: round` 平鋪」做法（那個做法要求邊條必須可平鋪、不能有獨特裝飾，跟四個角落各自要放不同功能圖示的需求衝突，所以換掉）。

### 6.1 角落素材：固定尺寸的獨立圖示，不是切自 frame 圖的一角

| 角落 | 內容 | 目前用哪張圖 |
|---|---|---|
| 左上 | 面板專屬圖示（每個面板不同） | `<素材前綴>_badge.png`（`b_badge.png`／`h_badge.png`／`n_badge.png`／`l_badge.png`，manifest 狀態已從 `reserved` 改成 `active`） |
| 右上 | 關閉鈕圖示（四個面板目前共用同一種視覺語言——藍底白 X） | `<素材前綴>_close.png` |
| 左下／右下 | 純裝飾邊角，不用圖片，CSS 畫 | 無（見 `panel-skins.css` 的 `.nw-corner::before`） |

這幾張 `_badge.png`／`_close.png` 尺寸不用跟 `.modal` 的邊框厚度或視窗尺寸有任何關係——它們是獨立的圖示素材，前端用 `background-size: contain` 塞進固定 `44px × 44px` 的角落容器（見 `NWL.md` §1.2 的 `--nw-corner-size`），素材本身只要是清楚可辨識的方形（或圓形置中）圖示即可，四張不用尺寸完全一致（目前實際尺寸從 96×100 到 129×139 不等，manifest §4.4 有實測值），前端已經用 `contain` 統一縮放進同一個容器。

新增面板的角落圖示時：裁一張獨立的方形圖示 PNG（背景透明），不用管邊條或其他角落，也不用另外切九宮格。

### 6.2 邊條材質：預設用 CSS 純色，不強制要圖片

`.modal.nw-frame` 的邊條是 CSS `border-color`（見 `NWL.md` §1.1），目前四個皮膚共用同一組藍頂／金邊配色。如果之後要幫邊條加材質質感（木紋、金屬拉絲），優先考慮用 CSS 漸層函式（`repeating-linear-gradient()` 之類）當 `border-image-source`，而不是用點陣圖片——CSS 漸層函式天生就是無限延伸、不會有拉伸/平鋪失真的問題，響應式安全這件事不用額外驗證。如果真的需要用點陣圖片做邊條材質，那張圖必須是可以左右/上下無縫平鋪的單一紋理單元（不能有任何只該出現一次的獨特圖案），並比照舊版 `border-image-repeat: round` 的做法接上——但目前沒有這個需求，先不做。

### 6.3 `b_frame.png` / `h_frame.png` / `n_frame.png` / `l_frame.png` 現況

這四張九宮格 frame 圖是上一版架構（`border-image` 九宮格）的產物，manifest 裡狀態還留著 `active`，但 `panel-skins.css` 目前**沒有任何規則引用它們**。先保留檔案（未來如果邊框要改回圖片材質，裡面的木紋/藍色調色可以參考），但視覺上不再生效，manifest 的 `target` 欄位已經跟 CSS 實際狀態脫節，等有明確去留決定（刪除或重新啟用）再更新。

## 7. 面板專屬素材 vs. 主題素材

`assets/panel-art/` 底下的素材（外框、格子紋理、按鈕圖示）目前**不隨主題切換**——一個面板的視覺皮膚是獨立於 `theme.json` 之外的另一套系統（`.modal-skin-<id>` class，見 NDL §9.2）。

這是目前的技術現實，不是刻意的最終設計——如果未來要讓面板皮膚也能跟著主題整套切換（例如「賽博龐克主題」連背包外框都要換成賽博風），需要把 `panel-art` 素材也移進 `themes/<id>/panel-art/` 底下、並修改 CSS 從 `modal-skin-<id>` 改成讀取當前主題的路徑。這件事還沒有排入範圍，這裡先記錄下來供之後規劃參考。

## 8. 素材缺失時的降級規則

延續 NDL §8：素材缺失不能讓介面壞掉或空白。

- 主題的 `assets.keys.<key>` 沒有填 → 保留該鍵位的內建 SVG 圖示，不報錯。
- 主題的 `assets.bg`/`minimap`/`avatars` 缺失 → 保留原本的預設背景/圖示。
- 面板皮膚（`panel-art`）的素材檔案不存在 → 該面板維持沒有皮膚時的預設扁平樣式（不要讓 `background-image: url(不存在的檔案)` 導致背景整塊空白，CSS 本身在圖片載入失敗時已經是「背景色透出來」的行為，只要記得幫每個用到面板專屬素材的元素都準備一個合理的 CSS `background-color` 當底，不要完全依賴圖片）。

## 9. 交付檢查表

新增或修改一份面板美術素材時，交付前確認：
